# @thomasfosterau/effect-wikimedia

## 0.4.0

### Minor Changes

- 34dee64: Send `origin=*` on every Action API (`/w/api.php`) request, so a browser page on another origin can read the response. Without an `origin` parameter MediaWiki sends no CORS headers on the Action API. This changes the query string of every `Action`, `Commons`, `Wikidata` and `Reconciliation` request, and makes them anonymous: MediaWiki answers as a logged-out user and ignores session cookies (as an on-wiki gadget would send) and any `Authorization` header added through `HttpClient.mapRequest`. `Rest` and `Sparql` requests are unchanged. An `origin` passed in `Core.WikimediaRequest.params` is sent in place of `*`.
- 30281f4: Send an `Api-User-Agent` header, with the same value as `User-Agent`, on every `Core.WikimediaClient` request, so every `Action`, `Rest`, `Commons`, `Wikidata`, `Sparql` and `Reconciliation` request carries it. Chromium-based browsers silently drop a `User-Agent` set on `fetch`, so until now a browser caller's `Core.UserAgent` never reached Wikimedia. Wikimedia's API etiquette asks browser clients to send `Api-User-Agent` instead, and browsers send it as given.

  In a browser this changes CORS behaviour: `Api-User-Agent` isn't a CORS-safelisted header, so cross-origin requests that Chromium sent as simple requests (`Rest` and `Sparql` GETs, and Action API GETs with `origin=*`) now get an `OPTIONS` preflight first. The Action API (with `origin=*`) and the REST API allow the header in their preflight responses, and WDQS's nginx config lists it too, though no live WDQS preflight has been checked. `Dumps.fromHttpRange` is unchanged and sends `User-Agent` only.

- 8ccb107: **Breaking:** `Reconciliation.normaliseCommonsImage` now returns `{ filename, iri }`, the same field names as `Reconciliation.ImageFact`, instead of `{ externalId, externalIri }`. The values are unchanged and no alias is kept for the old names.

  To migrate, rename the fields you read from the result: `externalId` → `filename` and `externalIri` → `iri`.

- 91ec393: Make the `User-Agent` configurable, with a neutral default. The new `Core.UserAgent` reference sets the header every `Core.WikimediaClient` request and every `Dumps.fromHttpRange` request sends, and `Dumps.FromHttpRangeOptions` gains a `userAgent` option that overrides it for one download. `Core.USER_AGENT`, the default, changes from `effect-wikimedia/0.0.0 (+https://github.com/thomasfosterau/website; mailto:me@thomasfoster.au)` to `effect-wikimedia (+https://www.npmjs.com/package/@thomasfosterau/effect-wikimedia)`: it names this package, not the package author, and drops the stale version. Wikimedia's User-Agent policy asks each caller to identify itself, so set your own, with your contact details: `Core.wikimediaLayer.pipe(Layer.provideMerge(Layer.succeed(Core.UserAgent, "my-bot/1.2 (bot@example.org)")))`.
- 0f05412: `Reconciliation.DateFact` has a `calendar` field: `"gregorian"` when the claim's Wikibase calendar model is proleptic Gregorian (`Q1985727`), `"julian"` when it is proleptic Julian (`Q1985786`), and `null` when the claim has no calendar model or names another one. Read `time` with `calendar`: a Julian date, common before 1582, is not the same day as the Gregorian date with the same digits. `WikidataLookup.enrich` sets it from each date claim's `calendarmodel` and accepts the `http` and `https` entity IRIs.

  `DateFact` first ships in this release, so no released version needs migrating. `calendar` is required: code that builds `DateFact` values itself, such as test fixtures, must set it (`null` for an unknown calendar), and a stored `Date` fact without it no longer decodes through `Reconciliation.WikidataFact` or `Reconciliation.DateFact`.

- 635ba6a: `Reconciliation.EXTERNAL_ID_AUTHORITIES` now checks each identifier against its authority's format before building the IRI, and percent-encodes it into a single path segment. Before, a value such as a P214 (VIAF) claim of `../../x` built `https://viaf.org/viaf/../../x`, which resolves to `https://viaf.org/x`. Each entry's `iri` now returns `string | null` (typed by the new `Reconciliation.ExternalIdAuthority`): it returns `null` for a value outside the authority's identifier format (VIAF, ISNI, ORCID, LCCN, GND, BnF; each at least as permissive as the property's Wikidata format constraint, with LCCN in the Library of Congress's normalised form), and `WikidataLookup.enrich` emits no `sameAs` fact for such a value. ISNI values in Wikidata's spaced form (`0000 0001 2103 2683`) now build the compact IRI `https://isni.org/isni/0000000121032683` instead of an IRI containing spaces.
- cb34135: `Action.getPageMetadata` (and `Action.normalisePageMetadata`) now return `null` for a title the Action API reports as `invalid`, such as `Foo<Bar`, and for a `Special:` or `Media:` title. Both used to return a `PageMetadata` with a `null` `pageId` and every other field except `title` `null`, because MediaWiki doesn't flag either entry `missing`. `getWikitext` and `parsePage` already return `null` for these titles. `PageMetadataResponse`'s page entries gain optional `invalid` and `special` fields. The `getPageMetadata` doc comment now states its error channel.
- 9db692e: **Breaking:** `Reconciliation.MAX_TEXT_FIELD_LENGTH` is renamed `Reconciliation.MAX_CANDIDATE_TEXT_LENGTH`, and `Reconciliation.sanitiseText` is renamed `Reconciliation.sanitiseCandidateText`, so they no longer share names with `Core.MAX_TEXT_FIELD_LENGTH` and `Core.sanitiseText`. Their behaviour is unchanged: the candidate bound is still 2000 code units, against Core's 4000, and the candidate sanitiser still collapses internal whitespace, which Core's does not (it only trims). The old names are removed with no deprecated aliases, so update any imports that use them.
- 68e1e61: `Wikitext.stripToText` now decodes every HTML5 named entity, as MediaWiki renders it: `&eacute;` becomes "é", `&copy;` becomes "©", `&AMP;` becomes "&", and `&NotEqualTilde;` becomes its two code points, U+2242 U+0338. Before, it decoded only `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;`, `&nbsp;`, `&ndash;`, `&mdash;`, `&hellip;`, `&times;` and `&deg;`, and kept every other named entity as written. MediaWiki's two aliases for `&rlm;`, spelt in Hebrew (`&רלמ;`) and in Arabic (`&رلم;`), now decode to U+200F as well. As in MediaWiki, names are case-sensitive and need their `;`, so `&Amp;` and `&eacute` (with no `;`) still stay as written.

  `Wikitext.parse` now reads a named entity whose name has non-ASCII characters, such as `&רלמ;`, as one `HtmlEntity` node, as MediaWiki does. Before, it read it as text. `Wikitext.serialize` and the template helpers give the same output as before, and so does `stripToText` for any such name other than the two `&rlm;` aliases above, but code that walks the AST (`walk`, `filter`) now sees the split. For example, French typography puts a no-break space (U+00A0) before `;`, so `AT&T ; Verizon` (with U+00A0 between `T` and `;`) now parses as text, an `HtmlEntity` for `&T ;`, then text.

  The entity table adds about 24 KB minified (about 12 KB gzipped) to a bundle that imports `Wikitext`. A bundle that imports only other namespaces does not include it.

  The package now also ships `THIRD_PARTY_NOTICES.md`, with the full license texts for the entity table: the HTML Standard's (BSD 3-Clause, as incorporated into source code) and `character-entities`' (MIT).

- 12a064b: The published declarations no longer import `node:stream`, so a browser or Worker project that type-checks them (`skipLibCheck: false`) no longer needs `@types/node`. The `Dumps` byte-source signatures now use two new structural types in place of Node's stream classes: `Dumps.fromNodeReadable` takes `() => Dumps.NodeReadableLike`, and `Dumps.Decompressor` is `() => Dumps.NodeDuplexLike`. Node streams such as `fs.createReadStream(...)`, `Readable.from(...)`, `zlib.createGunzip()` and any `Transform` still fit both, so code that passes them compiles unchanged. Code that uses what a `Decompressor` returns, such as `Dumps.gunzipTransform()`, now gets a `NodeDuplexLike` rather than a Node `Duplex`; cast it back to `Duplex` to call other stream methods on it.

  Because the structural type also admits plain objects, a `Decompressor` that returns a value `node:stream` doesn't recognise as a stream now fails `Dumps.fromFile` / `Dumps.decompressWith` with a `SourceError` instead of hanging (pass a real Node stream: the check is a heuristic, and a plain object with boolean `readable` / `writable` still hangs), and `Dumps.fromNodeReadable` fails with a `SourceError` when its `evaluate` throws rather than dying with a defect. Streams built from real Node streams behave as before.

- 9975ff7: `Wikitext.parse` no longer splits a table cell or caption inside a template, argument, wikilink, closed comment or extension tag (#132). Until now the cell structure was found by plain text search, so `| {{flag|France}}` parsed with `attrs: " {{flag"` and the plain text `France}}`, with no `Template` node, and `findTemplates`, `getParam`, `walk` and `stripToText` all missed the template. The same search split `| a || {{flagicon|FRA}}` and `| Paris<ref>{{cite web|url=x}}</ref>` at the template's pipe, read `| {{x||y}}` as two cells, and read each `|a=b` line of a multi-line `{{Infobox …}}` in a cell as a new cell. Now a `|` inside one of those constructs never splits attributes from content, a `||` or `!!` inside one never separates cells, and a line break inside one never starts a table line. So the template stays whole in the cell's `content`, and `attrs` holds only the text before a `|` outside them.

  This changes the tree for common tables: `TableCell.attrs` and `TableCaption.attrs` are now `undefined` for cells like the ones above, and a cell or row that held a multi-line template is now one cell or row. `serialize(parse(x)) === x` still holds, except for a caption after a row (#131), which more inputs now reach because more tables are recognised. A construct that spans a `|}` line now carries the table past it, and when no later `|}` follows there is no table. A bracket that never closes, or an unclosed `<!--`, is still ordinary text, so a stray `{{` in a cell doesn't hide the rest of the table. `[[` keeps its guard: a wikilink before the first `|` outside those constructs still means the cell has no attributes, and now a `||` inside a wikilink doesn't split the cell either.

- 29073da: `Reconciliation.WikidataFact` is now a union tagged by fact kind, built from `Schema` tagged structs, and drops the `mappingKind` and `notes` fields, which came from the website's mapping table. `WikidataLookup.enrich` returns, in order, one `Item` fact for the confirmed QID, then `Identifier`, `Date` and `Image` facts. `Reconciliation.WikidataFact` is also a schema with `match`, `guards` and `isAnyOf`, and each variant is exported as a schema and a type: `ItemFact`, `IdentifierFact`, `DateFact` and `ImageFact`.

  To migrate, branch on `_tag` instead of `authority` and `notes`:

  - QID self-link (`authority: "wikidata"`, `mappingKind: "exact"`): now `{ _tag: "Item", qid, iri }`, where `qid` was `externalId` and `iri` was `externalIri`.
  - `sameAs` identifier (`mappingKind: "exact"`): now `{ _tag: "Identifier", property, authority, value, iri }`, where `value` was `externalId`, `iri` was `externalIri`, and `property` (e.g. `"P214"`) is new.
  - Date (`notes` such as `"date of birth"`): now `{ _tag: "Date", property, label, time, precision, calendar }`, where `time` was `externalId`, `label` was `notes`, and `property` replaces `externalIri` (`wikidataEntityIri(property)` rebuilds the old value). `precision` is new: Wikibase's 0–14 precision code (9 = year, 11 = day), or `null`. `calendar` is new: `"gregorian"`, `"julian"` or `null`.
  - Image (`authority: "wikimedia-commons"`, `notes: "image"`): now `{ _tag: "Image", property, filename, iri }`, where `filename` was `externalId` and `iri` was `externalIri`. `filename` is the claim's own spelling: Wikibase `commonsMedia` values carry no `File:` prefix, and none is stripped.

- c4452bb: `Reconciliation.WikidataLookup` is now keyed `"effect-wikimedia/WikidataLookup"`, in the package's namespace like `Core.WikimediaClient` (`"effect-wikimedia/Client"`), instead of the app-style `"@app/WikidataLookup"` it was ported with. Code that uses the `WikidataLookup` class is unaffected; code that provides or reads the service by the raw key string must switch to the new key.

### Patch Changes

- 8ff70a0: `Core` no longer adds `origin=*` to an Action API request whose `params` already carry `crossorigin`, MediaWiki's authenticated-CORS mode. MediaWiki rejects a request that has both parameters with HTTP 403. The Action API path is now matched after URL normalisation, so a spelling like `/w/./api.php` also gets `origin=*`. The `WikimediaRequest` docs cover both, and the README now documents `crossorigin` on hand-built requests.
- be87f93: Document every `Action` property.

  - **Result interfaces.** The properties of `WikitextResult`, `PageMetadata`, `SearchResult`, `ParsedSection` and `ParsedPage` now say where each field comes from in the Action API response and when it is `null`. They also give its units and its form:
    - `PageMetadata.length` is in UTF-8 bytes.
    - `timestamp` and `touched` are ISO 8601 UTC strings, passed through unvalidated.
    - Titles are in prefixed display form, with spaces.
    - `ParsedPage.categories` are in database form, without the `Category:` prefix.
  - **HTML fields.** `SearchResult.snippet` and `ParsedSection.title` are documented as HTML that is not sanitised: escape or sanitise them before rendering. The `Action` module comment says so too.
  - **`PageMetadata.pageId`** notes that a title the API reports as `invalid` or `special` gets a result with a `null` page ID, not `null`.
  - **`WikitextResult`.** Its summary no longer says it can hold a requested (non-current) revision.
  - **Raw response schemas.** `WikitextResponse`, `PageMetadataResponse`, `SearchResponse` and `ParseResponse` stay in the docs, because the exported `normalise*` functions take them. Their fields now have short comments, and each schema's comment points to the typed result its normaliser builds.

  Doc comments only; no runtime or type change, and nothing is hidden from the docs.

- 82adb77: `Dumps.fromFile` and `Dumps.decompressWith` now accept a classic (pre-streams2) Node stream as the decompressor, such as the one `unbzip2-stream` returns, so Wikidata's `.json.bz2` dumps stream through `{ decompressor: () => unbzip2() }`. Such a stream emits `end` and `close` but never `finish`, and `stream.compose` failed it with a `SourceError` "Premature close"; it is now adapted into a `Duplex` first. A `Duplex` or `Transform` passes through unchanged. The `Decompressor` docs and the README show the bzip2 recipe.
- 4f3ce48: Document every `Core` property. The error fields now have doc comments: `InvalidRequest.kind` lists the kinds this package uses (`"host"`, `"title"`, `"filename"`, `"revisionId"`, `"entityId"`, `"query"`, `"language"`, `"type"`, `"queryLength"`, `"missingLimit"`), and `InvalidRequest.value` is the input as passed (a `"filename"` with any `File:` prefix removed; for `"queryLength"` and `"missingLimit"`, the query's length or its first 120 code units). `RequestFailed.description` is a log message whose three forms are listed. `RateLimited.retryAfterSeconds` is in seconds, from `Retry-After` or `DEFAULT_MAXLAG_SECONDS`, and uncapped. `RetryOptions` now gives its units and defaults, with the retry budget applying per request. Two class summaries were corrected: `InvalidRequest` also covers bad ids, queries and options, and `RateLimited` covers a `429` or `503` with or without `Retry-After`. No type is hidden from the docs, since `Core` exposes no raw response schema.
- ba6f7e4: Docs: the `Dumps.decodeEntityLine` doc comment now lists its `dumps/not-an-entity` cases as examples rather than a complete list, and names the one it left out: an object Wikibase flagged `missing`, which `Wikidata.decodeEntity` rejects even when its id is valid. Behaviour is unchanged.
- 644639c: `Dumps.decodeEntityLine` (and so `Dumps.entityRecords`) now reports a dump line whose body is the JSON literal `null` (`null,`) as `dumps/not-an-entity`, like any other valid JSON that is not an entity object (`42`, `"x"`, `[]`). Before, it reported `dumps/invalid-json`, because the internal parse step returned `null` both for a parse failure and for a body that parsed to `null`. A line that is not valid JSON is still `dumps/invalid-json`, and every other line decodes as before.
- 80187ee: Fix a crash in `Dumps.decompressWith`. When the upstream source had already failed and the stage was rejected (it isn't a Node stream), cancelling the errored web stream produced an unhandled promise rejection, which crashes a Node process. The rejection is now swallowed. The stream fails with the `SourceError` for the rejected stage, and the upstream's own error is not reported.
- f0c9bb6: `Dumps.decompressWith` (and so `Dumps.gunzip`) no longer leaks its upstream source when the stream is interrupted just before the decompression stage is opened. Before, the source (an HTTP body from `Dumps.fromHttpRange`, a file) had already been started, nothing stopped it, and it stayed open; an HTTP body kept its connection. It now starts in the same uninterruptible step that opens the stage, so stream teardown stops it.

  `Dumps.fromFile` on a compressed file, `Dumps.gunzip` / `Dumps.decompressWith`, and `Dumps.fromNodeReadable` over a `stream.compose` chain also no longer crash the process when the stream is torn down before it is first read. Destroying their decompression chain at that point emitted an `AbortError` that nothing listened for, which Node throws as an uncaught exception. The teardown now drops that error.

- 50dcf44: `Dumps.decompressWith` no longer leaves its upstream source open when the `Decompressor` returns a value that isn't a Node stream: the stream still fails with a `SourceError`, and the source (an HTTP range download, a file) is now cancelled and closed. `Dumps.fromFile` likewise destroys the decompressor it created when opening the file throws. The `Dumps.NodeDuplexLike` and `Dumps.Decompressor` docs now say what the runtime check covers: a value that `node:stream` doesn't recognise as a stream fails with a `SourceError`; pass a real Node stream.
- 7136ee3: `Dumps.decompressWith` and `Dumps.fromFile` no longer leak when the `Decompressor` returns a stream that is already used. A stage already destroyed, or one whose input had ended, failed the stream with a `SourceError` but left the upstream source (an HTTP range download, a file) open, or, in `fromFile`, the file descriptor. A stage whose output had already ended made `decompressWith` hang and `fromFile` succeed with no bytes. Such a stage now fails the stream with a `SourceError` before anything is opened. If Node's `stream.compose` rejects a stage anyway, the source or file it was given is now closed. The `Dumps.NodeDuplexLike` and `Dumps.Decompressor` docs now say the stage must be a new Node stream each time.
- f301cce: Fix doc-comment links that pointed at nothing: module-path links such as `{@link "./core".WikimediaRequest}` (including those in the `Dumps` overview, `Dumps.onlyEntities`, `Reconciliation.WikidataLookup`, and the module comments of the entity-dump and XML-dump pipelines and of the Node dump sources), links to helpers the package doesn't export (such as the branches named on `Reconciliation.normaliseFacts`), and a stale `labelText` reference on `Wikitext.ExternalLink` (now `stripToText`). Document `Core.WikimediaClient`'s `getJson` and `getText`, including their error channel. The namespace module comments end in a bare `@module`, so generated docs name each namespace as the barrel exports it (`Core`, not `core`). Doc comments only; no runtime or type change.
- e3c77f9: Document the `Dumps` record properties. Each field of `EntityHit`, `DumpLineError`, `PageRef`, `Contributor`, `Revision`, `PageRevisionHit`, `PageRevisionError` and `XmlToken`, and of `tokenizeXml`'s result, now has a doc comment saying what it holds, when it is `null`, and how it is bounded. Line numbers count every line of the decompressed dump, framing and blank lines included. A `DumpLineError`'s `raw` is cut to 500 UTF-16 code units. The XML reader's short fields are trimmed and cut to 4,096 UTF-16 code units, numeric fields are `null` unless they are a non-negative decimal integer of at most 18 digits and no larger than `Number.MAX_SAFE_INTEGER`, and `Revision.text` is neither trimmed nor cut. Three existing comments are corrected. `DumpLineError` no longer says a bad line never fails the stream: a line with a malformed nested container can still end it as a defect (#147). `PageRevisionError` now lists every case that produces it, including a stray `</revision>`. The entities module comment and `EntityHit.item` no longer overclaim: #147 can end the stream, and only `Q`, `P` and `L` ids decode (a MediaInfo or EntitySchema line is `dumps/not-an-entity`). `Revision` no longer says its content is always wikitext. Two current limitations are documented rather than fixed: a multi-slot revision's `model`, `format` and `text` come from its last slot, not the main one (#154), and the 16,777,216 cap that the `detail` message calls bytes counts UTF-16 code units (#155). Nothing else changes.
- 7b5c7da: `Core.WikimediaClient` now honours the `Retry-After` header on the Action API's `maxlag` error body, as it already did on a `429` or `503`. MediaWiki sends `Retry-After` set to the larger of the request's `maxlag` parameter and 5 seconds; the client used to ignore it and retry after `Core.DEFAULT_MAXLAG_SECONDS` (5), sooner than asked whenever the request's `maxlagSeconds` was above 5. Callers with the default `maxlagSeconds` (5) were not affected. `RateLimited.retryAfterSeconds` for a `maxlag` body is now the header's value when it is a number of seconds, and still 5 when the header is absent or an HTTP date. Each wait stays capped by `RetryOptions.maxDelaySeconds` (30 by default). The doc comments on `Core.detectMaxlagSignal` and `Core.RateLimited`, which said the header is not sent, are corrected, and `Core.DEFAULT_MAXLAG_SECONDS` now says it is also the fallback wait.
- 3d0a6bf: The npm page now gives a working contact. `bugs` is the maintainer's email (`me@thomasfoster.au`) instead of the private GitHub repository's issue tracker, `homepage` is the npm package page instead of the private repository's README, and the README has a Contact section with the same email.
- b38151c: `Dumps.fromNodeReadable` (and so `Dumps.fromFile`, `Dumps.gunzip` and `Dumps.decompressWith`) no longer leaks the Readable when the stream is interrupted just after opening it. Opening the Readable and registering its teardown are now one uninterruptible step, so an interruption that arrives right after the `evaluate` callback returns destroys the Readable. Before, the stream completed as interrupted and the Readable (a file descriptor, an HTTP body, a decompressor) stayed open.

- cb4d94d: Document every `Reconciliation` property. So do the `filename` and `iri` of `normaliseCommonsImage`'s result. No type is hidden from the docs, since `Reconciliation` exposes no raw response schema.
- 52b28ad: `Core.normaliseTitle` now rejects a title that contains a lone UTF-16 surrogate, which made `encodeURIComponent` throw `URIError`. `Rest`, `Action` and `Commons.getFileInfo` fail with `InvalidRequest` before any request (the `Rest` path builders previously died with a `URIError` defect, and `Action` sent the title with the surrogate replaced by U+FFFD), and `Commons.filePathUrl` and `Reconciliation.normaliseCommonsImage` return `null` instead of throwing. Valid surrogate pairs, such as emoji, are still accepted.
- 4f30063: Reject MediaWiki's relative-path titles (`.`, `..`, a leading `./` or `../`, a `/./` or `/../` anywhere, a trailing `/.` or `/..`) in `Core.normaliseTitle`. `new URL` removed `.` and `..` path segments, so `Rest.getPageMetadata(host, "..")` requested `/w/rest.php/v1/`, `Rest.getParsedHtml(host, ".")` requested `/w/rest.php/v1/page/html`, and `Commons.filePathUrl("..")` built `https://commons.wikimedia.org/wiki/`. `Rest`, `Action` and `Commons.getFileInfo` now fail with `InvalidRequest` before any request is sent; `Commons.filePathUrl` and `Reconciliation.normaliseCommonsImage` return `null`. - 10b2ad4: Document every `Rest` property. Each field of `PageMetadata` and `RevisionMetadata`, and of the lenient `PageMetadataResponse` and `RevisionMetadataResponse` schemas, now has a doc comment. Each says what the field holds and when it is `null`: `key` is the title in URL form with underscores and `title` the display form with spaces, timestamps are MediaWiki's ISO 8601 UTC strings passed through unparsed, `size` is in bytes, `pageTitle` is the page's current title (after any move), and `licenseUrl` is the wiki's site-wide content license rather than one specific to the page or revision. - 51e7428: Document every `Sparql` property. Each field of `UriTerm`, `LiteralTerm`, `BlankNodeTerm` and `UnknownTerm`, and of the lenient `SparqlResultsResponse` schema, now has a doc comment saying what it holds, when it is `null` or `""`, and how it is bounded: a term's `value` is cut at 10,000 UTF-16 code units, a literal's `datatype` at 2,000 and its `language` at 40, and none is trimmed or validated. `LiteralTerm.value` is the lexical form, never parsed into a number or a date. `SparqlResultsResponse` stays in the docs, because the exported `normaliseResults` takes it; its comment now says which malformed responses fail the decode (reported as `RequestFailed`) and points to the typed `SparqlResults`. `SparqlResults.vars` now says that entries that are not strings are dropped and each is cut at 200 UTF-16 code units. Nothing else changes; the comments on the schema fields also appear in the built JavaScript.
- 2372143: `Dumps.fromNodeReadable` (and so `Dumps.fromFile`, `Dumps.gunzip` and `Dumps.decompressWith`) now tears down a stalled source: interrupting the stream while the Readable is waiting for data destroys the Readable and completes once the Readable's own `destroy()` does, without waiting for that data. Before, the interruption hung and the Readable (a file descriptor, an HTTP body, a decompressor) was never released. The wait for `destroy()` to finish is bounded at one second: a source whose `destroy()` never emits `close` (a `Dumps.fromFile` read of a FIFO whose writer is open but idle, or a Readable built with `emitClose: false`) no longer holds the interruption up for more than a second, though the interruption may then complete before that source has released what it holds (a FIFO read keeps its file descriptor until the writer writes or closes).
- 380fa79: `Wikitext.stripToText` no longer replaces `&constructor;`, `&toString;`, `&valueOf;` or `&hasOwnProperty;` with the source of a built-in function, such as `function Object() { [native code] }`. Like any other unknown named entity, each is now kept as written.

  A numeric character reference that MediaWiki renders as literal text now also stays as written, so the result shows what a reader sees. This covers NUL, the C0 and C1 control characters other than tab and newline, carriage return, a surrogate, U+FFFE and U+FFFF. Before, `stripToText` decoded these references. A lone surrogate made the result malformed UTF-16, so `encodeURIComponent` threw `URIError`, and two surrogate references such as `&#55357;&#56832;` were joined into one character. A reference past U+10FFFF already stayed as written. A hand-built `HtmlEntity` whose `raw` is not a whole decimal or hex reference, such as `&#x41g;`, now stays as written instead of decoding the leading digits (it was "A").

- 780acc5: Document that a lone UTF-16 surrogate in a `WikimediaRequest.params` value is sent as U+FFFD, because `URLSearchParams` replaces it. A title is different: `Core.normaliseTitle` rejects one.
- be238c4: Document how to set `Core.UserAgent` so both request paths see it. `WikimediaClient` reads it when its layer is built, and `Dumps.fromHttpRange` reads it from the program's context. Two forms reach both:

No type is hidden from the docs: the two response schemas are the parameter types of the exported `normaliseEntities` and `normaliseSearch`, so a consumer can type against them. Nothing else changes; the comments on the schema fields also appear in the built JavaScript.
- 727c4e6: `Wikidata` now caps sitelinks, which its `MAX_LIST_ENTRIES` doc comment claimed but the code never did. - 15a9506: `Wikitext`: parse wikitables (`{| … |}`) into structured `Table`/`TableCaption`/`TableRow`/`TableCell` nodes, and recognise bare `http(s)://` URLs in running text as `AutoLink` nodes, closing both vocabulary deferrals from thomasfosterau/website#1287.

## 0.1.0

### Minor Changes

- 447fe5d: Initial release.

  A strongly typed, Effect-idiomatic client family for Wikimedia properties, as one package with a namespace per surface on a single barrel:

  - `Core` — the shared `HttpClient` service, per-wiki host validation, the typed error family, and the polite-`User-Agent` / `maxlag` / retry-after etiquette every other module builds on.
  - `Action`, `Rest`, `Commons` — the Action API, the Core REST/Parsoid surface, and Commons file info / `Special:FilePath` URLs.
  - `Wikidata` — the typed item / claim model (branded `Q`/`P`/`L` ids, the full snak datavalue union) plus batched `wbgetentities` and `wbsearchentities`.
  - `Sparql` — the Wikidata Query Service client, with a LIMIT-enforcing helper.
  - `Wikitext` — a pure, dependency-free wikitext → typed AST parser, round-trip serializer, and query surface.
  - `Dumps` — Wikimedia dump processing as `Stream` pipelines, with Node-only byte sources and pluggable decompression.
  - `Reconciliation` — Match/Enrich against Wikidata: label and external-identifier lookup to candidate items, then fact enrichment for a confirmed QID.

  Importing one namespace never pulls another surface's code into a bundle; `tests/tree-shaking.test.ts` proves it with real `esbuild` builds.

  Extracted from `thomasfosterau/website`, where it had been in production use; its pre-extraction git history is preserved.
